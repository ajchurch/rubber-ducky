# B1. Discover 5 unique weak/vulnerable security implementations.

## 1) Weak password storage (fast/unsalted hashing)
Cryptographic functions like SHA-256 are meant to compute in microseconds. If a database is breached, an attacker's offline hardware could run brute-force and dictionary attacks at an uncontrollable scale.  A salt is a random, unique string added to each password before it is hashed. Without a salt, two users with the same password will have the exact same hash and if one were to be cracked, all accounts with that password are exposed, and attackers can easily utilise rainbow tables to find out said passwords.

## 2) Poor SQL Implementation
SQL injections are frequently abused by attackers for those who have not protected against string concatenation and other forms of sql injection. An attacker can then make its own user input, a part of the SQL query syntax. 

An sql query could be built something like this:
"SELECT * FROM users WHERE username='" + user + "' AND password='" + pass + "'"
which is then executed, if the user were to input something like admin' -- as the username, it would comment out the password check entirely, allowing them to log in. More advanced attackers might do payloads that can dump tables, modify data, or drop the database entirely. 

## 3) Hardcoded credentials in source code or config files
A developer writes DB_PASSWORD = "password123" directly in settings.py, or embeds an AWS access key in a mobile app's compiled binary. The repo gets pushed to GitHub which is sometimes public, or sometimes internal but later exposed. Secrets in source code are visible to everyone with repo access, persist in Git history even after it has been 'removed' and can't be rotated without a code change. GitHub's secret scanning service finds thousands of leaked AWS keys every month.
